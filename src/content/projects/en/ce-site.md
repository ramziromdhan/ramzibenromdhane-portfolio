A cybersecurity portfolio has to withstand a technical review. This site is therefore treated like a production service: a minimal architecture, a threat model and a chain of automated controls.

## Architecture

![Architecture diagram: the developer pushes code to GitHub, the CI chain checks it, and Cloudflare Pages builds and deploys the site to visitors](/diagrams/ce-site-architecture-en.svg)

The site is generated by Astro and hosted on Cloudflare Pages. There is no application server, no database and no user account: the attack surface comes down to the domain, the DNS, the host and the build chain.

On every push and pull request, GitHub Actions checks the code, while Cloudflare Pages builds and deploys the main branch. DNS is managed by Cloudflare, and the contact address is an email forward to my personal mailbox.

## Threat model and measures

| Risk | Measure |
| --- | --- |
| Content injection (XSS) | Strict content security policy, without `unsafe-inline`, and no third-party script in the code |
| Embedding in another page | `frame-ancestors 'none'` and `X-Frame-Options` |
| Traffic interception | HTTPS everywhere and HSTS |
| Secret leaks | Gitleaks on every push and pull request |
| Vulnerable dependencies | `npm audit`, Trivy scan and Dependabot, with a waiting period before adopting a brand-new version |
| CI chain compromise | GitHub Actions pinned by commit hash and minimal permissions |
| Vulnerability reporting | `security.txt` file |

Response headers are defined in a `_headers` file versioned with the code. Style sheets are emitted as separate files and the only script on the site is a local file, which allows a policy without inline styles or scripts.

## Results

- The site builds in 2 to 4 seconds locally and generates fully static pages.
- The build output contains no inline style sheet or script (apart from JSON-LD structured data), which makes the strict policy enforceable.
- No third-party resource is loaded by the site code: fonts, scripts and images are all served by the site itself.

## Planned improvements

- Measure and publish the securityheaders.com and Mozilla Observatory grades.
- Explicitly handle the audience-measurement script the host can add: disable it, or allow it in the policy.
- Enable DNSSEC and lock the domain.
- Publish SPF and DMARC for the contact address.
- Protect the main branch, so that CI actually blocks a deployment when it fails.

## Lessons learned

A strict policy has a cost: code blocks are not syntax-highlighted, because highlighting would inject inline styles. Automatic additions by the host must also be handled explicitly, by allowing or disabling them, because a strict policy does not tolerate silent additions.
